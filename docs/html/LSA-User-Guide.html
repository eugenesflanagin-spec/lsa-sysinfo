1. What it is, in plain words

LSA measures how fast your computer can move data between the processor and its memory.

It does this for four places where data can live:

  • Memory - your RAM sticks. Big, but the slowest.
  • L1 cache - a tiny, very fast store inside each CPU core.
  • L2 cache - bigger and a bit slower, also per core.
  • L3 cache - bigger again, shared by many cores.

For each place it measures four things:

Test Plain words Unit
Read How much data per second the CPU can read. MB/s (memory) or GB/s (caches)
Write How much data per second the CPU can write. MB/s or GB/s
Copy How much data per second it can read and write back somewhere else. MB/s or GB/s
Latency How long one single, unpredictable read takes. Lower is better. ns (nanoseconds)

The result is a 4 x 4 grid, laid out like the familiar AIDA64 Cache & Memory Benchmark window, so you can compare a Linux run with a Windows run on the same PC.

This is the first tool of LSA. The project plans more of AIDA64's pages and tools later (CHECKLIST.tsv lists 162 planned items), but today LSA is the Cache & Memory Benchmark only.

2. Who it is for

  • Beginners who want one number to check their RAM is running at the speed they paid for (for example after turning on XMP or EXPO in the BIOS).
  • Tuners and overclockers who change memory timings, Infinity Fabric clock (FCLK) or similar BIOS settings and want to see the effect.
  • Dual-booters who want to compare Linux with Windows, or LSA with AIDA64, on the same machine.
  • Developers and reviewers who want a scriptable command-line benchmark with plain text output.

3. Install

LSA runs on 64-bit x86 Linux (Intel or AMD). It needs GTK 3 for the window. The command line needs only glibc.

3.1 Arch Linux and derivatives - AUR

The package name is lsa-sysinfo. With an AUR helper:

yay -S lsa-sysinfo

or by hand:

git clone https://aur.archlinux.org/lsa-sysinfo.git
cd lsa-sysinfo
makepkg -si

3.2 Arch Linux - prebuilt package from the release

Each GitHub release has lsa-sysinfo-<version>-1-x86_64.pkg.tar.zst. Install it with:

sudo pacman -U lsa-sysinfo-0.2.0-1-x86_64.pkg.tar.zst

3.3 Any other distribution - generic tarball

Each release also has lsa-sysinfo-<version>-linux-x86_64.tar.gz. It was built on an older distribution (Ubuntu 22.04), so it runs on most current ones (glibc 2.34 or newer, GTK 3). The fast AVX2 / AVX-512 code is picked at run time, only if your CPU has it.

tar xzf lsa-sysinfo-0.2.0-linux-x86_64.tar.gz
cd lsa-sysinfo-0.2.0-linux-x86_64
./usr/bin/lsa --version          # try it without installing
./usr/bin/lsa-gui
sudo cp -r usr/bin usr/share /usr/local/     # install for all users

Read INSTALL.txt inside the tarball for the full list of run-time needs.

3.4 Build from source

You need gcc, make, pkg-config and the GTK 3 development files (Arch: gtk3; Debian/Ubuntu: libgtk-3-dev; Fedora: gtk3-devel).

git clone https://github.com/eugenesflanagin-spec/lsa-sysinfo.git
cd lsa-sysinfo
make native                         # builds dist/native/lsa and dist/native/lsa-gui
make install                        # per-user install into ~/.local
# or, system-wide (what the Arch package does):
sudo make install-system DESTDIR= SYSPREFIX=/usr

make install puts the programs in ~/.local/bin. Make sure that folder is on your PATH.

3.5 Optional: memory details from srs-sysinfo

LSA can show your memory type and speed (for example "Dual Channel DDR5-6000 SDRAM (2 DIMMs)"). Reading that needs root, so LSA borrows it from a small cache file written by srs-root, part of the sister project srs-sysinfo:

yay -S srs-sysinfo        # or install it from its own release
pkexec srs-root            # one password prompt; writes ~/.cache/srs/root/dmidecode.txt

Without it, the benchmark works fine. Only the "Memory Bus", "DRAM:FSB Ratio" and "Memory Type" lines stay empty.

4. First launch

Open your application menu and look for LSA Cache & Memory Benchmark (category System / Monitor; on some desktops under Benchmarks). Or type lsa-gui in a terminal.

The window opens with an empty grid and the system lines filled in. Nothing runs yet.

The window before a run, on the author's Ryzen 7 7800X3D. The grid fills in, cell by cell, when you press Start Benchmark.

Before you press Start Benchmark:

  1. Close heavy programs - games, browsers with video, compiles, virtual machines, file copies. Anything that uses the CPU or memory makes the results lower and less steady.
  2. Never run another memory benchmark at the same time - for example AIDA64 under Wine, or a second copy of LSA. Both runs would fight for the memory bus and both results would be wrong (latency can double).
  3. Press Start Benchmark. A dialog warns that every CPU thread and the memory bus will be busy for about 20 seconds. Press OK.

The run takes about 20 seconds. The cell being measured turns yellow and shows ..., and the status line says, for example, Measuring L2 Cache Copy .... Your PC may feel slow during the run. That is normal.

To stop early, press the same button (it now says Stop). Closing the window also stops the run.

6. What each number means

6.1 Read, Write, Copy (bandwidth)

Bandwidth is how much data moves per second. Think of it as the width of a motorway: more lanes, more cars per second.

  • Read - the CPU pulls data in. This is what most programs do most.
  • Write - the CPU sends data out.
  • Copy - read from one place and write to another. LSA counts both the bytes read and the bytes written, the usual convention for this kind of benchmark. So Copy is often close to Read + Write's combined traffic, not half of it.

Units:

  • Memory is shown in MB/s (megabytes per second), e.g. 67678 MB/s.
  • Caches are shown in GB/s (gigabytes per second), e.g. 2292.3 GB/s, because the numbers are huge.
  • LSA uses decimal units: 1 MB = 1,000,000 bytes and 1 GB = 1,000 MB. The command line can show binary units instead (--mib).

All bandwidth tests use every CPU thread at once. So the number is the whole CPU's total, not one core's.

6.2 Latency

Latency is the waiting time for one piece of data. Think of it as how long one car takes to drive from A to B, no matter how wide the road is.

  • It is measured in nanoseconds (ns). 1 ns = one billionth of a second.
  • Lower is better.
  • It uses one thread only, reading in a random order so the CPU cannot guess what comes next.

Typical values on a current desktop:

Level Typical latency Why
L1 about 1 ns (4-5 CPU clock ticks) Inside the core, right next to it.
L2 about 3-4 ns Still per core, a bit further away.
L3 about 10-12 ns Shared by many cores.
Memory about 60-90 ns (DDR5), 55-80 ns (good DDR4) Off the CPU chip, through the memory controller to the RAM sticks.

6.3 Example: a full result

This is a run from the author's PC (Ryzen 7 7800X3D, 2 x 16 GB DDR5-6000), taken from the saved run history and shown in the command line's layout:

Linux System Audit 0.1.3 - Cache & Memory Benchmark

                     Read          Write           Copy      Latency
Memory          67678 MB/s     93211 MB/s     67373 MB/s      81.8 ns
L1 Cache       2292.3 GB/s    1279.0 GB/s    2459.7 GB/s       0.8 ns
L2 Cache       1240.2 GB/s    1198.0 GB/s    1215.6 GB/s       3.9 ns
L3 Cache       764.39 GB/s    637.68 GB/s    715.16 GB/s      11.6 ns

How to read it:

  • The caches are 10 to 35 times faster than memory. That is why caches exist.
  • L1 Write is about half of L1 Read. Each core can do two reads but only one write per clock tick.
  • Memory latency (81.8 ns) is about 100 times L1 latency (0.8 ns).

7. How the tests work (the detail)

You do not need this to use LSA. It explains why the numbers look the way they do.

7.1 Bandwidth tests

  • LSA starts one worker thread per logical CPU and pins each one to its own CPU ("pinned" = it is not allowed to move to another CPU).
  • Each thread works on its own block of memory:
    • L1, L2, L3: the block is half of that thread's share of the cache, so it stays inside that cache level.
    • Memory: a block far bigger than all caches (at least 4 x L3, at least 256 MB, default 1 GB, at most a quarter of free RAM), so the data cannot sit in a cache.
  • Each test runs many short trials of about 40-80 ms over about 1 second per cell, and keeps the best trial. Best, not average, because background activity can only make a trial slower.
  • Memory Copy uses streaming stores (writes that bypass the cache), as is usual for memory-to-memory copies.

7.2 Memory Write on AMD CPUs (CLZERO)

On AMD Zen CPUs the link between each core complex and the memory controller can only accept about 16 bytes of normal writes per fabric clock. Normal "streaming" writes stop there (about 33 GB/s on a 7800X3D), well below what the RAM can absorb.

AMD CPUs have an instruction called CLZERO that writes a whole 64-byte line of zeros straight to memory. LSA uses it for Memory Write when the CPU has it: one thread per physical core, threads interleaved in 4 KB chunks over a shared block (256 MB or 2.5 x L3), best full pass. That measures what the memory itself can take, about 93,000 MB/s on the author's PC, which matches the reference.

  • Other CPUs (Intel, older AMD) use streaming stores.
  • To see the streaming-store figure on AMD, use lsa cachemem --mem-write stream.
  • The command line's last line says which method was used.

7.3 Latency test

  • One thread follows a random chain of pointers through every 64-byte line of a block. Each read tells it where the next read is, so the CPU cannot prefetch (fetch early) the data.
  • Block sizes:
    • L1: half of the L1 data cache.
    • L2: half of the L2 cache.
    • L3: 8 x the L2 size (mostly L3 hits, still within the reach of the address-translation cache).
    • Memory: 8 x L3, at least 256 MB, at most half of free RAM. With 8 x L3 only about 1 in 8 reads can still hit L3.
  • Page size: caches use normal 4 KB pages. Memory uses 2 MB huge pages (Linux "transparent huge pages") so that address-translation misses do not inflate the figure.

7.4 Code paths (AVX-512, AVX2, SSE2)

LSA has three versions of its read/write/copy loops and picks the widest one your CPU supports:

Code path Bytes per instruction CPUs
AVX-512 64 AMD Zen 4 and newer, some Intel
AVX2 32 Most CPUs since about 2013-2015
SSE2 16 Every 64-bit x86 CPU

The status line and the last command-line line show which one was used. Cache bandwidth depends strongly on it; memory bandwidth hardly does. You can force a narrower one on the command line (--isa avx2) to compare.

  • .txt - the same results as text, in this layout:

8.2 Command-line output

lsa cachemem prints progress to the terminal's error stream (one line per finished cell) and the final grid plus the system lines to normal output. So you can save just the result with:

9. Reading results and comparing runs

9.1 Rules for a fair comparison

  1. Same machine, same settings. Change one thing at a time (one BIOS setting, one kernel).
  2. Idle machine. Close other programs. Wait a minute after boot for background jobs to settle.
  3. Run 3 times and look at the spread. On the author's PC the history shows L1 Read between 2178 and 2292 GB/s on normal runs. A difference smaller than the spread is noise.
  4. Look for outliers. One run in the history has L1 Read 1903 GB/s and L3 Read 1171 GB/s, way off the others: something else was running. Throw such runs away.
  5. Compare like with like. Do not compare an AVX-512 run with an AVX2 run, or a run with --threads 8 with an all-thread run.

9.2 What changes what

You changed... Expect to see change in...
Memory speed (MT/s), XMP/EXPO Memory Read/Write/Copy up, Memory Latency down
Memory timings (CL, tRCD...) Mostly Memory Latency
AMD FCLK / UCLK ratio (UCLK 1:1 vs 1:2) Memory Latency and Memory Read/Copy
CPU clock (PBO, Curve Optimizer, power limits) L1/L2/L3 bandwidth and latency in ns
Fewer DIMMs or single channel Memory bandwidth roughly halves
Background load Everything drops and gets noisy, L3 and Memory most

The author's own history shows one such change: Memory Latency went from 76-77 ns (block 4 x L3, LSA 0.1.2) to 80-82 ns (block 8 x L3, LSA 0.1.3). That was a measurement change, not a hardware change: with the bigger block fewer reads accidentally hit the L3 cache. Always note the LSA version when you compare old and new runs.

10. Known limits and known differences from AIDA64

  • L1 Read is about 5% below AIDA64. About 2250 GB/s vs 2445 GB/s on a 7800X3D. One core alone reaches about 61 bytes per clock tick, but with all cores loaded LSA gets about 289 GB/s per core against AIDA64's about 305. Longer runs (--seconds 5), one thread per core, 256-bit loads and per-thread buffer offsets were all tried; none closed the gap without pushing other cells away from the reference. So it is left as measured. See CHANGELOG.md.
  • Every other cell is within about 3% of AIDA64 on the reference system.
  • Other CPUs are less tested. The matching work was done on one AMD Zen 4 X3D system. Intel CPUs and other AMD generations work, but their numbers have not been compared side by side.
  • Memory Write on non-AMD CPUs uses streaming stores, so it may read lower than AIDA64 on those.
  • North Bridge Clock is read only on AMD Ryzen 7000 desktop CPUs (PM table version 0x540104) with the ryzen_smu driver loaded; elsewhere it shows n/a and the reason. CPU FSB is measured on Linux when the CPU has an invariant TSC and ACPI CPPC; otherwise, and always on Windows, it shows 100.0 MHz (nominal).
  • Memory type and speed need the srs-root cache (see 3.5).
  • Windows latency is higher than Linux latency unless Windows grants large pages (see section 11).
  • Only the Cache & Memory Benchmark exists so far. The other AIDA64 pages are planned.

11. Windows build

LSA also builds for 64-bit Windows, so you can run the same engine on the same PC under Windows and compare.

11.1 Install

Each release has two Windows files:

  • lsa-sysinfo-<version>-setup.exe - installer. Installs for your user only, no administrator rights needed, into %LOCALAPPDATA%\Programs\Linux System Audit. Adds a Start-menu folder "Linux System Audit" with LSA Cache & Memory Benchmark and an uninstall shortcut. A desktop shortcut is optional (a tick box in the installer). It also appears in Settings -> Apps.
  • lsa-sysinfo-<version>-win64-portable.zip - no install. Unzip anywhere and run.

Both contain:

  • lsa-gui.exe - the Cache & Memory window (native Win32, no runtime needed).
  • lsa.exe - the command line, same options as Linux (lsa cachemem ...).
  • LSA-User-Guide.html - this guide (the installer adds a Start-menu shortcut to it). The Guide button and F1 in the window open it.

Windows SmartScreen may warn about an unknown publisher, because the files are not code-signed.

11.2 Differences on Windows

  • Save writes a BMP picture plus a TXT file (Linux: PNG + TXT).
  • The run history is %LOCALAPPDATA%\LSA\cachemem-history.txt.
  • Memory details come from SMBIOS directly (no admin and no srs-root needed).
  • CPU FSB shows 100.0 MHz (nominal) and North Bridge Clock n/a: neither is read on Windows.
  • Latency and large pages: the memory latency test uses 2 MB large pages only if your Windows account has the "Lock pages in memory" right. Without it LSA falls back to 4 KB pages, which adds address-translation time, so Memory Latency reads higher. The status line says which was used. To grant it: run secpol.msc -> Local Policies -> User Rights Assignment -> Lock pages in memory -> add your user, then sign out and in again. (secpol.msc exists on Pro / Enterprise editions.)

11.3 Uninstall on Windows

Settings -> Apps -> Linux System Audit -> Uninstall, or the uninstall shortcut in the Start menu folder. The portable zip: just delete the folder. The history file in %LOCALAPPDATA%\LSA stays; delete it by hand if you want.

13. Troubleshooting

Problem What to do
Numbers much lower than expected, or very different between runs Something else is using the CPU or memory. Check with top or a system monitor. Close it, wait, run again. Laptops: plug in the charger and use a performance power profile.
Memory Latency is 120-160 ns, far above normal Another memory benchmark (for example AIDA64 under Wine, or a second LSA) is running at the same time. Run only one.
Memory Bus / Memory Type say "run srs-root once" or "unknown" Install srs-sysinfo and run pkexec srs-root once (see 3.5). Restart the window.
Memory speed shows lower than your kit's rating (e.g. 4800 instead of 6000) Your BIOS is not using the XMP / EXPO profile. Enable it in the BIOS.
"could not allocate the test memory" (command line) Not enough free RAM. Close programs and try again. (--mem-mib cannot go below 256 MiB or 4 x L3.)
Memory Latency higher than expected on Linux Transparent huge pages may be off. Check cat /sys/kernel/mm/transparent_hugepage/enabled; it should show [always] or [madvise], not [never].
Status line says SSE2 or AVX2 on a CPU that has AVX-512 Some CPUs have AVX-512 turned off in the BIOS or by microcode. LSA uses what the CPU reports.
The window does not open from the terminal over SSH It needs a desktop session. Use the command line lsa cachemem instead.
lsa runs a different program (prints a file list) Your shell has an alias or function called lsa (some zsh and fish setups use it for ls -a). Run command lsa cachemem, use the full path /usr/bin/lsa, or remove the alias.
Windows: Memory Latency higher than on Linux Grant "Lock pages in memory" (see 11.2).

14. Uninstall

  • Arch (AUR or package): sudo pacman -R lsa-sysinfo
  • Generic tarball in /usr/local: remove the files listed in the tarball, for example sudo rm /usr/local/bin/lsa /usr/local/bin/lsa-gui /usr/local/share/applications/lsa-cachemem.desktop /usr/local/share/icons/hicolor/256x256/apps/lsa.png and sudo rm -r /usr/local/share/doc/lsa-sysinfo /usr/local/share/licenses/lsa-sysinfo
  • make install (per user): remove the same files under ~/.local.
  • Your data: rm -r ~/.cache/lsa deletes the run history. Saved PNG/TXT files are wherever you saved them.
  • Windows: see 11.3.

15. FAQ

Is LSA the same as AIDA64? No. It is an independent, clean-room program that measures the same things in the same layout, so the numbers can be compared. It is not made by FinalWire and contains nothing from AIDA64.

Can it damage my PC? No more than any heavy program. It only reads and writes ordinary memory it allocated itself. It does not change any setting, clock or voltage. The run lasts about 20 seconds; the CPU gets warm like under any full load.

Why is Copy bigger than Read? Copy counts bytes read plus bytes written. For caches that adds up to more than Read alone.

Why are caches in GB/s and memory in MB/s? To match the familiar layout, and because cache figures would have too many digits in MB/s.

Why is my Memory Write much higher than Memory Read? On AMD CPUs with CLZERO, Memory Write measures the memory's own write speed (see 7.2). Reads have to come all the way back to the cores through the fabric, writes of zeros do not.

Does it need root? No. Only the optional memory details come from a root-made cache (srs-root).

Can I run it from a script? Yes: lsa cachemem prints plain text. It asks before it starts; add --yes in scripts (without a terminal and without --yes it does not start). See CLI-REFERENCE.md.

Why does the window say OctalCore? That is the core count written as a word (8 cores = Octal), as in the classic report style.

Does it work on ARM? No. The benchmark loops are x86-64 only.

16. Glossary

The full glossary is in GLOSSARY.md. The most important words:

  • Bandwidth - how much data moves per second. Higher is better.
  • Latency - how long one read takes. Lower is better.
  • Cache (L1, L2, L3) - small, fast memory inside the CPU that keeps recently used data close.
  • MB/s, GB/s - megabytes / gigabytes per second (decimal: 1 MB = 1,000,000 bytes).
  • ns - nanosecond, one billionth of a second.
  • CLZERO - an AMD instruction that writes a whole 64-byte line of zeros to memory.
  • AVX-512 / AVX2 / SSE2 - sets of wide CPU instructions that move 64 / 32 / 16 bytes at a time.
  • srs-root - the root helper from srs-sysinfo that saves memory details LSA can read.

Linux System Audit - Result Reference

Back to the User Guide - Command-line reference - Glossary

One short section for every value LSA shows: the 16 cells of the grid and the lines below it. In the window, right-click a value and choose Open guide, or point at it and press F1, to jump straight here. On the command line, lsa guide ITEM does the same (lsa guide --list shows the items).

Each section starts with the plain-English meaning, then the detail. Example figures are from the author's PC (Ryzen 7 7800X3D, 2 x 16 GB DDR5-6000, FCLK 2133) unless a section says otherwise.

Memory Read

mem-read - grid cell, bandwidth

In plain words: how much data per second the whole CPU can read from your RAM sticks. Higher is better.

  • Every CPU thread reads its own part of a block far bigger than all caches (default 1 GB in total, at least 4 x L3, at most a quarter of free RAM), so the data really comes from RAM.
  • Shown in MB/s (1 MB = 1,000,000 bytes). Example: about 67,700 MB/s.
  • What moves it: memory speed (MT/s), number of channels, on AMD the fabric clock (FCLK, see North Bridge Clock) and UCLK ratio, background load.
  • Detail: How the tests work.

Memory Write

mem-write - grid cell, bandwidth

In plain words: how much data per second the CPU can write to RAM. Higher is better.

  • On AMD CPUs with the CLZERO instruction LSA writes whole zeroed 64-byte lines straight to memory, one thread per physical core. That measures what the memory itself can take: about 93,000 MB/s on the example PC.
  • Other CPUs use streaming stores (writes that bypass the caches). --mem-write stream shows that figure on AMD too; it is much lower there (about 33,000 MB/s), because of the link between the cores and the memory controller.
  • Detail: Memory Write on AMD CPUs.

Memory Copy

mem-copy - grid cell, bandwidth

In plain words: how fast the CPU can read data from one place in RAM and write it to another.

  • LSA counts both the bytes read and the bytes written, the usual convention, so Copy is close to Read rather than half of it. Example: about 67,400 MB/s.
  • The writes are streaming stores. Same factors as Memory Read.

Memory Latency

mem-latency - grid cell, latency

In plain words: how long the CPU waits for one single, unpredictable read from RAM. Lower is better.

  • One thread follows a random chain of pointers through a block of 8 x L3 (at least 256 MB, at most half of free RAM) on 2 MB pages, so the CPU cannot guess the next address.
  • Shown in ns (nanoseconds). Example: about 80-82 ns. Typical DDR5: 60-90 ns.
  • What moves it: memory timings (CL, tRCD, ...), memory speed, FCLK and the UCLK ratio.
  • If it reads 120-160 ns, another memory benchmark is probably running at the same time.
  • Detail: Latency test.

L1 Cache Read

l1-read - grid cell, bandwidth

In plain words: how fast all cores together read from their own tiny, fastest cache.

  • Each thread works on half of its L1 data cache. Shown in GB/s. Example: about 2250-2330 GB/s.
  • Depends on the CPU clock and the code path (AVX-512 reads 64 bytes per instruction, AVX2 32).
  • Known difference: about 5% below AIDA64 on the reference system. See Known limits.

L1 Cache Write

l1-write - grid cell, bandwidth

In plain words: how fast all cores together write into their L1 cache.

  • About half of L1 Read (example: about 1280 GB/s), because a core can do two reads but only one write per clock tick.

L1 Cache Copy

l1-copy - grid cell, bandwidth

In plain words: read and write inside the L1 cache at the same time.

  • Counts bytes read plus bytes written, so it can be higher than Read. Example: about 2460 GB/s.

L1 Cache Latency

l1-latency - grid cell, latency

In plain words: the wait for one read that hits the L1 cache.

  • One thread, random pointer chase over half of L1d. Example: 0.8 ns, about 4-5 clock ticks. It only changes with the CPU clock.

L2 Cache Read

l2-read - grid cell, bandwidth

In plain words: how fast all cores together read from their L2 caches (bigger and a bit slower than L1, still one per core).

  • Each thread works on half of its share of L2. Example: about 1240 GB/s.
  • Depends on the CPU clock.

L2 Cache Write

l2-write - grid cell, bandwidth

In plain words: how fast all cores together write into their L2 caches.

  • Example: about 1200 GB/s. Depends on the CPU clock.

L2 Cache Copy

l2-copy - grid cell, bandwidth

In plain words: read and write inside the L2 cache at the same time (bytes read plus bytes written).

  • Example: about 1215 GB/s.

L2 Cache Latency

l2-latency - grid cell, latency

In plain words: the wait for one read that hits the L2 cache.

  • Random pointer chase over half of L2, 4 KB pages. Example: 3.6-3.9 ns.

L3 Cache Read

l3-read - grid cell, bandwidth

In plain words: how fast all cores together read from the L3 cache, the big cache the cores share.

  • Each thread works on half of its share of L3. Example: about 700-760 GB/s.
  • Depends on the CPU clock and, more than L1/L2, on background load (other programs use L3 too).

L3 Cache Write

l3-write - grid cell, bandwidth

In plain words: how fast all cores together write into the shared L3 cache.

  • Example: about 640 GB/s.

L3 Cache Copy

l3-copy - grid cell, bandwidth

In plain words: read and write inside the L3 cache at the same time (bytes read plus bytes written).

  • Example: about 715 GB/s.

L3 Cache Latency

l3-latency - grid cell, latency

In plain words: the wait for one read that hits the L3 cache.

  • Random pointer chase over 8 x the L2 size. Example: about 11.6 ns.

CPU Type

cpu-type - system line

In plain words: which processor you have, with the core count written as a word.

  • Example: OctalCore AMD Ryzen 7 7800X3D (8 cores = Octal). From /proc/cpuinfo (Windows: CPUID).

CPU Stepping

cpu-stepping - system line

In plain words: the CPU's design name and revision.

  • Example: Raphael, stepping 2 (family 19h model 61h). The code name comes from a built-in table of public CPU IDs; unknown CPUs show only family, model and stepping.

CPU Clock

cpu-clock - system line

In plain words: how fast one core was actually ticking a moment ago.

  • LSA measures it with a short timing loop (it is not the number on the box). Example: about 4850-4970 MHz. It moves a little from run to run, because modern CPUs change clock all the time.

CPU FSB

cpu-fsb - system line

In plain words: the base (reference) clock that the CPU clock is a multiple of. Usually 100 MHz; some boards let you raise it (on ASUS AM5 boards this is "eCLK").

  • Linux: measured as TSC rate x 100 / the CPU's nominal frequency (/sys/devices/system/cpu/cpu0/acpi_cppc/nominal_freq). The TSC is a counter that runs at the CPU's nominal clock times the base clock / 100, so this gives the real base clock. Example: 105.0 MHz on a board set to eCLK 105.
  • It needs an invariant TSC (constant_tsc in /proc/cpuinfo) and the ACPI CPPC nominal_freq file. Without them LSA shows 100.0 MHz (nominal).
  • Windows: always 100.0 MHz (nominal) - not measured.

CPU Multiplier

cpu-multiplier - system line

In plain words: how many times faster than the base clock the core runs.

  • CPU Clock / CPU FSB. Example: 4846 MHz / 105.0 MHz = 46.16x.
  • When the FSB is the nominal 100 MHz, it is CPU Clock / 100.

North Bridge Clock

nb-clock - system line

In plain words: on AMD Ryzen, the speed of the Infinity Fabric (FCLK), the internal link between the cores and the memory controller. A faster fabric helps memory bandwidth and latency.

  • Read from the PM table of the ryzen_smu kernel driver (/sys/kernel/ryzen_smu_drv/pm_table), read-only. Example: 2133.0 MHz (FCLK 2133).
  • Only the PM table layout 0x540104 (Ryzen 7000 desktop, Zen 4) is known to LSA. Other cases show why the value is missing:
    • n/a (ryzen_smu driver not loaded) - the driver is not installed or not loaded.
    • n/a (PM table version 0x...... not supported) - a CPU whose table layout LSA does not know.
    • n/a (ryzen_smu pm_table not readable) - the file exists but this user may not read it.
  • Windows: not read (n/a).

Memory Bus

memory-bus - system line

In plain words: the real clock of your RAM, half the "MT/s" figure on the box.

  • Example: 3000.0 MHz for DDR5-6000.
  • Linux: from the root DMI cache written by srs-root (srs-sysinfo), because reading it needs root. Without it the line says run srs-root once for DIMM data. Windows: from SMBIOS.

DRAM:FSB Ratio

dram-fsb - system line

In plain words: how many times faster than the base clock the memory clock is.

  • Memory Bus / CPU FSB. A whole ratio is shown as 30:1; otherwise with one decimal, for example DRAM:FSB 28.6:1 (3000 MHz / 105.0 MHz).
  • Needs the Memory Bus value (see above).

Memory Type

memory-type - system line

In plain words: the kind of RAM, its speed and how many sticks and channels.

  • Example: Dual Channel DDR5-6000 SDRAM (2 DIMMs). Same source as Memory Bus.
  • If the speed is lower than your kit's rating, XMP / EXPO is probably off in the BIOS.

Chipset

chipset - system line

In plain words: the motherboard's support chip and the CPU platform.

  • Example: AMD X870, AMD Raphael/Granite Ridge. The chipset model comes from the board name, the platform from the PCI root complex name in hwdata pci.ids.

Motherboard

motherboard - system line

In plain words: who made your motherboard and its model name.

  • From /sys/class/dmi/id/board_vendor and board_name (Windows: SMBIOS).

BIOS Version

bios - system line

In plain words: the version and date of the firmware that starts the PC.

  • From /sys/class/dmi/id/bios_version and bios_date (Windows: SMBIOS). Example: 1805 (09/18/2026).

Code path

code-path - status / last command-line line

In plain words: which set of CPU instructions the test loops used, and how many threads.

  • AVX-512 (64 bytes per instruction), AVX2 (32) or SSE2 (16): the widest your CPU has, unless --isa asked for a narrower one. Cache bandwidth depends on it strongly, memory bandwidth hardly.
  • The command line also lists the cache sizes LSA read from the kernel and the Memory Write method.
  • Detail: Code paths.

Options for cachemem

Option Default What it does
--threads N all logical CPUs Use only N worker threads for the bandwidth tests (on CPUs 0..N-1 of the allowed set). Values of 0, negative, or more than the CPU count mean "all". Latency always uses 1 thread.
--seconds S 1 Measuring time per cell, in seconds. Longer runs do not change the result much (5 s gives the same figures as 1 s on the reference PC); they mostly cost time.
--isa avx512|avx2|sse2 widest the CPU supports Force a narrower code path. Asking for one the CPU lacks falls back to the best it has. Any other word stops with an error that lists the valid values.
--mem-mib M auto (1024 MiB, capped at a quarter of available RAM) Total size of the Memory bandwidth block, in MiB, for all threads together. Use a smaller value on PCs with little free RAM. --tests LIST all tests Measure only these tests. Comma-separated words: read, write, copy, latency (lat also works).

--yes, -y off Start without asking. Needed when there is no terminal (scripts, cron). The environment variable LSA_TEST_NOCONFIRM does the same.
--mem-write auto|clzero|stream auto How Memory Write is measured. auto: CLZERO on AMD CPUs that have it, streaming stores elsewhere. stream: always streaming stores (shows the core-to-memory link limit on AMD). clzero: same as auto (CLZERO is used only if the CPU has it).

Linux System Audit - Glossary

Back to the User Guide - Command-line reference

Plain-English meanings of the words used in the LSA documents, A to Z.

  • AIDA64 - a system information and benchmark program for Windows made by FinalWire Ltd. LSA copies its Cache & Memory Benchmark layout so results can be compared. LSA is not affiliated with FinalWire.
  • AVX2 - "Advanced Vector Extensions 2". CPU instructions that handle 32 bytes at once. Found on most x86 CPUs since about 2013-2015.
  • AVX-512 - CPU instructions that handle 64 bytes at once. Found on AMD Zen 4 and newer and on some Intel CPUs. Gives the highest cache bandwidth figures.
  • Bandwidth - how much data moves per second. Like the number of lanes on a road. Higher is better.
  • Best-of trials - LSA repeats each measurement many times and keeps the fastest. Interruptions only ever make a trial slower, so the fastest one is the truest.
  • BIOS / UEFI - the firmware that starts the PC and holds settings such as memory speed.
  • Bytes per clock - how many bytes a core moves in one tick of its clock. A way to compare results at different clock speeds.
  • Cache - small, very fast memory inside the CPU that keeps copies of recently used data, so the CPU does not have to wait for RAM.
  • Cache line - the unit a cache works in: 64 bytes on current x86 CPUs. Reading one byte brings the whole 64-byte line in.
  • CCD / core complex - on AMD Ryzen, a chip (die) holding up to 8 cores and their L3 cache.
  • Chipset - the motherboard's support chip(s) that provide extra USB, SATA and PCIe connections.
  • CLZERO - an AMD instruction that writes a whole 64-byte line of zeros to memory without first reading it. LSA uses it to measure Memory Write on AMD CPUs.
  • Code path - which version of LSA's test loops is used: AVX-512, AVX2 or SSE2.
  • Copy - reading data from one place and writing it to another. LSA counts both the bytes read and the bytes written.
  • DDR4 / DDR5 - the two current generations of desktop memory. DDR5 is faster in bandwidth; latency is similar.
  • DIMM - one memory stick.
  • DMI / SMBIOS - tables in the firmware that describe the PC (board, BIOS, memory sticks). Reading the memory part needs root on Linux.
  • dmidecode - the Linux tool that reads DMI / SMBIOS tables. srs-root runs it and saves the output so LSA can read it without root.
  • DRAM - "dynamic RAM", the kind of memory on your memory sticks.
  • DRAM:FSB ratio - memory clock divided by the reference clock (FSB). DDR5-6000 runs its memory clock at 3000 MHz, so with a 100 MHz FSB the ratio is 30:1 (28.6:1 at 105 MHz).
  • Dual channel - two independent paths between the CPU and memory. Twice the bandwidth of one. Usually means one stick in each of two channels.
  • eCLK - on ASUS AM5 boards, the BIOS setting for the CPU's reference clock. Raising it from 100 MHz raises the CPU clock with it; LSA shows it as CPU FSB.
  • EXPO / XMP - memory profiles stored on the sticks (EXPO by AMD, XMP by Intel). Turning one on in the BIOS runs the memory at its rated speed instead of a slow default.
  • Fabric / Infinity Fabric - the internal link on AMD CPUs that joins the cores to the memory controller and the rest of the chip.
  • FCLK - the Infinity Fabric clock on AMD CPUs. Higher FCLK usually lowers memory latency.
  • FSB - "front side bus". In older PCs the bus between CPU and chipset; today used as the name for the reference clock (normally 100 MHz) that the CPU multiplier is applied to. LSA measures it on Linux from the TSC and the CPU's nominal frequency.
  • GB/s - gigabytes per second. 1 GB/s = 1,000 MB/s in LSA.
  • GiB/s, MiB/s - binary units: 1 MiB = 1,048,576 bytes. Shown with --mib.
  • Huge pages / transparent huge pages (THP) - memory pages of 2 MB instead of 4 KB. Fewer pages means fewer address translations, so memory latency measures the memory, not the translation.
  • L1 cache - the first, smallest and fastest cache, inside each core (32-48 KB for data on current CPUs). Latency about 1 ns.
  • L2 cache - second level, per core, about 0.5-2 MB. Latency about 3-4 ns.
  • L3 cache - third level, shared by many cores, 16-128 MB. Latency about 10-12 ns. "X3D" AMD CPUs have an extra-large stacked L3 (96 MB on a 7800X3D).
  • Latency - the waiting time for one piece of data. Lower is better.
  • Lock pages in memory - a Windows user right needed for large pages. Without it LSA's Windows build measures memory latency on 4 KB pages, which reads higher.
  • Logical CPU / thread - what the operating system sees as a CPU. With SMT, each core shows as two logical CPUs.
  • MB/s - megabytes per second. In LSA 1 MB = 1,000,000 bytes.
  • Memory controller - the part of the CPU that talks to the memory sticks.
  • MT/s - mega-transfers per second, the speed rating of memory (DDR5-6000 = 6000 MT/s). The actual memory clock is half of it.
  • Multiplier - CPU clock divided by the reference clock (e.g. 46.16 x 105 MHz = 4847 MHz).
  • Nominal frequency (CPPC) - the CPU's rated base clock as the firmware reports it through ACPI CPPC (/sys/devices/system/cpu/cpu0/acpi_cppc/nominal_freq), counted at a 100 MHz reference.
  • ns (nanosecond) - one billionth of a second.
  • North Bridge clock - on old PCs the chipset's clock; on current AMD CPUs the Infinity Fabric clock (FCLK). LSA reads it from the ryzen_smu PM table on Ryzen 7000 desktop CPUs.
  • Page / page walk - memory is managed in pages (4 KB normally). Finding where a page really is takes a "page walk", which costs time if it is not cached.
  • Pinned thread - a thread that is not allowed to move to another CPU. Keeps measurements steady.
  • PM table - a block of live values (clocks, voltages, power) that the AMD SMU publishes. The ryzen_smu driver makes it readable at /sys/kernel/ryzen_smu_drv/pm_table. Its layout changes between CPU generations, so LSA only reads the layout it knows (version 0x540104).
  • Pointer chase - a chain where each value read is the address of the next read. The CPU cannot guess ahead, so each step shows the full latency.
  • Prefetch - the CPU fetching data before it is asked for, because it guessed the pattern. Good for programs, bad for latency tests, so LSA uses a random chain.
  • RAM - the main memory of the PC.
  • Read - the CPU fetching data from a cache or memory.
  • ryzen_smu - an optional Linux kernel driver that gives read access to the AMD SMU's PM table.
  • SMT - "simultaneous multithreading" (Intel calls it Hyper-Threading). One core runs two threads.
  • SMU - AMD's "System Management Unit", a small processor inside the CPU that controls clocks and power. LSA never sends it commands; it only reads the PM table through ryzen_smu.
  • srs-root - the root helper from the sister project srs-sysinfo. Run once, it saves root-only hardware data (including memory details) into ~/.cache/srs/root.
  • SSE2 - CPU instructions that handle 16 bytes at once. Every 64-bit x86 CPU has them.
  • Stepping - the revision number of a CPU design.
  • Streaming store - a write that goes straight to memory without being kept in the cache. Used for big copies so the cache is not filled with data that will not be read again.
  • TLB - "translation lookaside buffer", a small cache of recent address translations. A TLB miss means a page walk.
  • TSC - "time stamp counter", a CPU counter that ticks at a fixed rate (the nominal clock) on current CPUs (constant_tsc). LSA times it to measure the FSB.
  • UCLK - on AMD CPUs, the memory controller clock. "1:1" means it runs at the memory clock; "1:2" means half. 1:1 gives lower latency when the memory can be run that way.
  • Write - the CPU sending data to a cache or memory.
  • X3D - AMD CPUs with an extra cache chip stacked on top ("3D V-Cache"), giving a very large L3.
